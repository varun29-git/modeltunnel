# Terminus Lean 150M dense-FP8, 10B-token run

This is the authorized full run using the existing eight-language, math, and code token set. The 10B view is a deterministic prefix of the shuffled, checksummed packed corpus; no documents are re-tokenized. The frozen tokenizer, 25-layer model, DeepGEMM/FA3/Triton kernels, and Muon optimizer are unchanged from the 2026-10-01 real-token H100 benchmark.

`plan.py generate --microbatch 48` defines a 393,216-token optimizer update (48 sequences × 4,096 tokens × 2 accumulation steps × one H100). This microbatch gave 250,956 real tokens/s and roughly 5.29 GB of memory headroom; microbatch 50 was only 0.5% faster with 1.36 GB headroom. The 10B WSD schedule preserves the 3B plan's proportions: 1B warmup, 7B stable, and 2B cosine decay to 10% of peak LR. The copied 0.01 pilot peak LR remains an empirical trial, especially with Muon at this width.

The full token budget is 9,999,998,976 usable tokens after sequence alignment. The midpoint is update 12,716 at 5,000,134,656 tokens; the final update is 25,432. The launcher stops once at midpoint, writes and audits an immutable checkpoint, then resumes the same run and finishes. Recovery checkpoints are written every 1,000 updates, with extra checkpoint/validation at the midpoint and final update. `resume_prepare.py` archives and removes telemetry beyond the last durable checkpoint before any replay.

The persistent run directory contains a copy of the plan/config, environment receipt, native preflight, validated full-scope manifest view, per-update `events.jsonl` (loss, gradient norm/clipping, LR, throughput and GPU memory), every-tenth-update `stability.jsonl` (layer activations, attention, FP8 and update ratios), `incidents.jsonl`, held-out language/domain validation every 100 updates, checkpoint files with SHA-256 receipts, and midpoint/final audits. `launch.sh` mirrors these artifacts to S3 every five minutes and on exit. Token shards and checkpoints live on the Azure **managed** disk mounted at `/srv/terminus-10b`; Azure's `/mnt` resource disk is ephemeral and can obscure a nested mount during boot.

The separate `terminus-lean-10b-finalize.service` runs alongside training and waits for `terminus-lean-10b.service` to exit successfully. It requires the final 25,432-update audit and both milestone checkpoint receipts, then hashes **every regular file** in the run directory (including all checkpoint and log files). It uploads the directory to the private Azure Blob `runs/terminus_lean_150m_10b_run_20261001/` prefix using the VM's managed identity and AzCopy `--put-md5`, and checks each remote file's length and Content-MD5 through Blob HEAD. It uploads and verifies an inventory, a `blob_verified.json` receipt, and its own finalizer log. Only then does it request Azure VM deallocation. A failed upload, missing file, changed local file, checksum mismatch, missing audit, or unsuccessful training service exit leaves the VM allocated; systemd retries the finalizer after five minutes. The Blob receipt is the durable proof of which files were verified.

The VM has a system-assigned managed identity with Storage Blob Data Contributor on the `t3logse388e1b8d9e3` storage account and Virtual Machine Contributor on this H100 VM. Install the finalizer unit into `/etc/systemd/system/`, create `/srv/terminus-10b/ops` owned by `azureuserboss`, and enable/start the unit. `python3 experiments/terminus_lean_150m_10b/finalize_blob_and_deallocate.py --run-root /srv/terminus-10b/runs/lean_dense_10b_20261001 --blob-url https://t3logse388e1b8d9e3.blob.core.windows.net/runs/terminus_lean_150m_10b_run_20261001/ --vm-resource-id /subscriptions/6ac11955-aa2f-4cf9-a693-e388e1b8d9e3/resourceGroups/H100_GROUP/providers/Microsoft.Compute/virtualMachines/h100 --status` reports the gate without uploading or deallocating.

The launch gate is the completed AWS `packed/manifest.json`, all train/validation shards, licenses and shuffle receipt at `s3://quark-research-repository-storage/data/modeltunnelv2_tokensets_20261001/packed/`. `prepare_views.py` validates every shard checksum, tokenizer identity, mixture and full campaign scope against the final 10B view. `launch.sh` must run under the H100 environment with `DATA_ROOT`, `RUN_ROOT`, `S3_RUN_URI`, `PYTHON`, `PYTHONPATH`, `CUDA_HOME`, and `DG_JIT_CACHE_DIR` set. It requires AWS credentials with read access to the data and write access to the run mirror; no credentials are stored in this repository.
