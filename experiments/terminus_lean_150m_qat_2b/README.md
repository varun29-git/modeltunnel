# Terminus Lean 150M: 2B-token ternary QAT continuation

This experiment starts from the SHA-verified final checkpoint of the 10B dense-FP8 run (`3d116e88…67f2144684b`). It retains the 25-layer, width-640 architecture, DeepGEMM and FP8 activations, and changes the effective projection weights to fully ternary (`weight_mode="ternary"`, strength 1). FP32 latent weights and Muon optimizer moments are carried into a new QAT phase. All three peak base learning rates are halved from 0.01 to **0.005**; the transition explicitly replaces the dense checkpoint's saved optimizer-group base rates after loading its moments.

The owner selected **2B QAT tokens**. This is equal to the dense run's 2B decay, not twice it; twice would be 4B. The QAT schedule is a fresh 200M warmup, 1.4B stable, and 400M cosine decay to 10% peak. The 48 × 4,096 × 2 batch decomposition yields 1,999,998,976 usable tokens and 5,087 updates. Validation stays every 100 updates, stability probes every 10, and recovery checkpoints every 500. The stage records an initial transition checkpoint and a final checkpoint.

The packed S3 corpus holds 12.890B train tokens, including 2.890B unused after the dense run. English has only 748M unused, so a fresh 2B stage cannot retain 50% English. This stage uses **37% English, 13% code, 13% math, 37% Indic** (5.3% for six languages and 5.2% Telugu). `prepare_views.py` calculates each source's exact consumed sequence count from the dense manifest's deterministic mixing schedule and starts QAT there. It reuses the original checksummed token shards and validation split without retokenizing or copying the corpus. The view receipt records every source offset and exposure. The trainer's phase counters restart at zero because the parent ended on a partial microbatch; the transition receipt records the parent counters and explicit reset. Optimizer moments and RNG state are retained.

The launcher verifies data, runs native ternary preflight, converts the checkpoint, trains with exact resume, and audits the completed run. It mirrors artifacts to S3 every five minutes and does a final sync before successful exit. The systemd finalizer then syncs again, uploads the mirror log, and checks the remote size and stored S3 checksum of every visible run file, including all checkpoints and training logs. It saves and uploads `s3_verified.json`. Next it hashes every run file, uploads to Azure Blob with Content-MD5, verifies every remote size/MD5, and only then deallocates the H100. Any failed gate leaves the VM allocated for diagnosis and retry.

The run is a **single QAT trial**, not evidence that 2B tokens, the changed mixture, the copied learning rate, or this schedule is optimal. The dense checkpoint's first attention norm scale was unusually small; compare its QAT stability and held-out source losses with the archived dense trajectory before promoting the model.
